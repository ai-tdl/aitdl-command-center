# RULE-BOOK Compliance Audit — Implementation Plan

Full audit of the PrathamOne Academy OS against the 9 RULE-BOOK files (CORE CONSTITUTION Laws 1–9, plus domain rules 01–07). Every bug and violation found in the current codebase is catalogued below with the specific law it breaks, and a concrete fix.

---

## Violations Found

### 🔴 CRITICAL: LAW 3 Violation — Hardcoded State Names in fees.py

**Law:** *"No `if (status == ...)` or hardcoded state names are allowed in application code (Python/JS)."*

**Location:** `backend/routers/fees.py`, lines 415–420 and 453–456 and 481 and 591 and 687

```python
# LINE 416 — BAD: State guard using hardcoded state names
if current_state in ("PAID", "WAIVED", "REFUNDED"):

# LINE 454 — BAD: Hardcoded event codes as Python strings
new_event = "FULL_PAYMENT" if current_state == "DEMAND_RAISED" else "BALANCE_CLEARED"

# LINE 456 — BAD
new_event = "PARTIAL_PAYMENT" if current_state == "DEMAND_RAISED" else "ADDITIONAL_PAYMENT"

# LINE 481 — BAD: Infer new_state in Python from a calculated value
"new_state": "PAID" if outstanding <= 0 else "PARTIALLY_PAID",

# LINE 591 — BAD: Guard on hardcoded state
if demand["current_state"] != "PAID":

# LINE 687 — BAD: Check state
if row["current_state"] == "OVERDUE":
```

**Fix:** The state-check guard on lines 416 and 591 should query `workflow_transitions` to determine if the action is allowed, rather than hardcoding states. The event code lookup (lines 453–456) must be replaced by querying available transitions from the workflow engine, not by Python if/else on state strings. The `new_state` on line 481 should be dropped from the response (the client must re-query for state, not have it inferred here). The `OVERDUE` check on line 687 is summary UI logic — acceptable as a label, but it should use the live state returned from DB.

**Proposed Fix:** Replace the state-guard checks with a call to the existing `WorkflowEngine.get_available_transitions()` to determine what transitions are valid. If a matching transition exists, use its `event_code` from the database row (not a Python string literal). For the `"PAID"/"PARTIALLY_PAID"` inference on line 481, just drop it — the client should call `GET /workflow/state/...` to learn the new state.

---

### 🔴 CRITICAL: LAW 4 Violation — Policy Enforced in Python Code instead of policy_master

**Law:** *"No business logic or eligibility rules may be embedded in the code. All conditional rules must be stored in `policy_master` and evaluated by the kernel before any workflow transition occurs."*

**Location:** `backend/routers/fees.py`, lines 505 and 584

```python
# LINE 505 — BAD: Business rule percentage hardcoded in Python
if body.concession_pct > 20 and role != "TENANT_ADMIN":

# LINE 584 — BAD: Role name hardcoded in Python for refund gate
if role != "TENANT_ADMIN":
```

**Fix:** These rules (`CONCESSION_AUTHORITY` and `REFUND_AUTHORITY`) should be stored as rows in `policy_master` and evaluated via the kernel's `execute_workflow_transition()` (or a `evaluate_policy()` call). Since a `policy_master` query helper already exists in `policy.py`, the check should call that. 

However — because the kernel's `execute_workflow_transition()` should already enforce policies, the explicit Python-level role guard is secondary defense. The immediate fix is:
1. Remove the hardcoded `20` threshold — look it up from `system_settings` with key `CONCESSION_AUTHORITY_MAX_PCT` (already seeded in db/24_module_04_fee_data.sql).
2. Replace the Python `role != "TENANT_ADMIN"` check with a `policy_master` DB lookup via the existing `policy.py` helper.

---

### 🟡 HIGH: LAW 5 Violation — DEBUG print statements leaking PII

**Law:** *"Every data mutation must trigger a hash-chained audit event."* *(Implied privacy: no PII or credential data should be printed in logs.)*

**Location:** `backend/routers/auth.py` lines 88, 144; `backend/middleware/tenant.py` lines 92, 94

```python
# auth.py line 88 — prints username being attempted (PII leak)
print(f"DEBUG: Attempting login for username: {form_data.username}")

# auth.py line 144 — prints user_id, tenant_id, role in plain logs
print(f"DEBUG: Login success for user={user_id} tenant={tenant_id} role={role}")

# tenant.py line 92 — prints role, tenant_id on every request
print(f"DEBUG: Middleware extracted role={request.state.role} tenant=...")

# tenant.py line 94 — prints JWT errors
print(f"DEBUG: JWT Error for path {request.url.path}: {e}")
```

**Fix:** Remove all `print(f"DEBUG: ...")`  statements. Replace with `import logging; logger = logging.getLogger(__name__)` and use `logger.debug(...)` so that debug output is controlled by log-level configuration and not always-on in production.

---

### 🟡 HIGH: Role Dropped on Token Refresh

**Law:** LAW 2 (Tenant Sovereignty) — identity must be consistently derived from the signed token.

**Location:** `backend/routers/auth.py`, line 175

```python
# BAD: Hardcodes "app_user" — the real role is in the refresh token payload
access_token = _create_token(
    {"sub": payload["sub"], "tenant_id": payload["tenant_id"], "role": "app_user", ...},
```

**Fix:** The refresh endpoint must re-embed the role from the refresh token payload or re-query the DB for the user's current role (preferred). The simplest compliant fix is to query the DB for the user record's `role_name` attribute during refresh, same as login does.

---

### 🟡 HIGH: Wrong Column in `_fetch_eav` Helper

**Location:** `backend/routers/entities.py`, line 345

```python
# BAD: column does not exist on entity_attribute_values
WHERE  eav.entity_record_id = $1
```

**Fix:** The column on `entity_attribute_values` is `record_id`, not `entity_record_id` (confirmed by the schema in `_fetch_eav_full` on line 373 which correctly uses `eav.record_id`). This means `_fetch_eav` (used internally) always returns empty — a silent data integrity failure.

## Proposed Strategy

### Database Simulation Script (PL/pgSQL)

Since we need to test concurrency (which inherently involves multiple active transactions), standard PL/pgSQL `DO` blocks run sequentially within a single transaction. To simulate race conditions and deadlocks without an external multi-threaded driver, we will use a combination of `pg_sleep`, autonomous transactions (via `dblink` or `pg_background` if available, or theoretical multi-window instructions), and logical lock contention scenarios. 

Given the constraints of standard PostgreSQL scripts, the script will be documented as a **Multi-Session Execution Guide** with explicit copy-paste blocks for Session A and Session B, accompanied by a single-file automated simulation that uses sequential exception handling to prove the presence of `FOR UPDATE` locks and `SERIALIZABLE` isolation constraints.

2.  **Concurrency Assertions**: Verify that `fees_ledger` is under `SERIALIZABLE` isolation.
3.  **Logical Simulation Blocks**: 
    - Freeze vs Insert Race
    - Freeze vs Approval Race
    - Double Approval Race
    - Cross-Tenant Concurrency
    - Reverse Entry under Freeze
4.  **Deadlock Simulation Instructions**: Specific steps to trigger a classic deadlock on the ledger to prove row-level locks are taking effect before timeouts.

# Add rewriteNavLinks() + Fix Hardcoded Domain URLs

Dev-time utility to rewrite all hardcoded `ganitsutram.com` domain links to
`localhost` equivalents when `GanitConfig.IS_DEV` is `true`. Zero impact in
production — the guard `if (!GanitConfig?.IS_DEV) return;` exits immediately.

## Proposed Changes

---

### ui-core / ganit-ui.js

#### [MODIFY] [ganit-ui.js](file:///d:/IMP/GitHub/ganitsutram/websites/ui-core/js/ganit-ui.js)

1. **Fix line 15** — The file currently destructures from `window.GanitConfig`
   at parse time:
   ```js
   const { API_BASE, PORTAL_URL } = window.GanitConfig;
   ```
   These variables are never actually used anywhere in the file (all other
   code reads `GanitConfig.*` directly).  
   **Fix:** Remove this destructure line — it risks a crash if `config.js`
   has not yet executed when the browser parses `ganit-ui.js`.

2. **Add `rewriteNavLinks()`** (exactly as specified) before the `GanitUI`
   object definition.

3. **Call it first in `initCoreSystems()`**:
   ```js
   function initCoreSystems() {
       rewriteNavLinks();   // ← NEW — must be first
       window.GanitUI.sendBeacon('page_view', ...);
       ...
   }
   ```

### portal / gate.html

#### [MODIFY] [gate.html](file:///d:/IMP/GitHub/ganitsutram/websites/portal/gate.html)

Six persona cards have hardcoded `data-url` attributes. These are read by
`GanitUI.gate.select()` in `ganit-ui.js` to set `selectedPersona.url`, which
is then used in `window.location.href = selectedPersona.url`.

**Fix:** Replace all six `data-url` values using template-literal-style
`GanitConfig.*` calls rendered into the HTML via an inline `<script>` block
that runs on `DOMContentLoaded`, OR (preferred — simpler) by updating
`GanitUI.gate.proceed()` in `ganit-ui.js` to apply the domain map before
redirecting.

> [!IMPORTANT]
> **Chosen approach: rewrite in `ganit-ui.js`'s `gate.proceed()`**.  
> `gate.proceed()` already calls `window.location.href = selectedPersona.url`.  
> We add the same domain-rewrite logic there so gate.html HTML stays clean and
> production-static. This is consistent with the existing `rewriteNavLinks()`
> approach for `<a href>` attributes.
>
> Since `rewriteNavLinks()` only rewrites `<a[href]>` and `[action]`
> attributes — not `data-url` attributes — we need to also rewrite `data-url`
> in `rewriteNavLinks()`, OR rewrite at the point of use (in `gate.proceed()`).
>
> **Decision: rewrite `data-url` inside `rewriteNavLinks()`** so all rewrites
> are in one place and there's one consistent code path.

Add to `rewriteNavLinks()` (after form actions):

```js
// Rewrite data-url attributes (used by persona cards in gate.html)
document.querySelectorAll('[data-url]').forEach(el => {
    const dataUrl = el.getAttribute('data-url');
    for (const [domain, localUrl] of Object.entries(domainMap)) {
        if (dataUrl.startsWith(domain)) {
            el.setAttribute('data-url', dataUrl.replace(domain, localUrl));
            break;
        }
    }
});
```

## Backend Framework Decision

### 🏆 Recommendation: FastAPI (Python)

Three clear reasons for AITDL specifically:

| | FastAPI (Python) | Fastify (Node.js) | Express (Node.js) |
|---|---|---|---|
| AI/ML native | ✅ Yes — same Python as your AI products | ❌ Needs bridge | ❌ Needs bridge |
| Auto API docs | ✅ Swagger at `/docs` — zero extra work | Needs plugin | Needs plugin |
| Input validation | ✅ Pydantic — built-in, strict | Needs JSON Schema | Needs library |
| Speed | 🚀 Very fast (async) | 🚀 Very fast | 🐢 Slower |
| Free tier cold starts | ✅ Fine on Railway/Render | ✅ Fine | ✅ Fine |
| When you add AI chatbot/recommendations later | ✅ Just import — no bridge | ❌ HTTP call to Python | ❌ HTTP call to Python |
| Learning curve | Medium (Python) | Low (JS) | Very Low (JS) |

> **Verdict:** Since AITDL builds AI products (Ganitsutram, My AI Pathsala, AI POS), the backend will eventually need Python ML libraries anyway. Start with FastAPI now — no migration needed later. If Jawahar is more comfortable with JS, use **Fastify** (strictly better than plain Express).

# V3 Modular Ecosystem Architecture

This document serves as the implementation blueprint for transitioning AITDL from a monolithic application into a highly modular ecosystem platform.

## 1. System Understanding

The platform must host multiple autonomous applications (products) while providing shared core services (auth, database, routing). It must accommodate a universal plugin system powered by event hooks, a scalable AI gateway for hybrid model access, and isolating UI themes for each product interface.

## 2. Core Loaders (`backend/services/`)

### `product_loader.py`
Scans the `products/` directory for `product.json` manifests on startup.
- Mounts each product's frontend static assets under `/app/{product_name}`
- Discovers and includes `backend/router.py` if present in the product directory.
- Bootstraps the desired theme from `themes/`.

### `plugin_loader.py`
Scans `plugins/` for `plugin.json` manifests.
- Injects frontend plugin assets (JS/CSS) dynamically into the DOM via Jinja2 templates or HTML parsing.
- Discovers `hooks.py` and registers callback functions against core system events.

### `hooks.py` (Event Registry)
Provides an interface for core code to trigger events, and plugins to listen:
```python
def trigger(event_name: str, *args, **kwargs): ...
def register(event_name: str, callback: callable): ...
```
Key hooks: `on_user_signup`, `on_lead_created`, `on_payment_completed`, `on_admin_login`.

## 3. Product & Plugin Isolation

Products and plugins must **never** mutate core files (`main.py`, `routers/admin.py`, etc.).
All features must be appended at runtime:
1. **Routing:** Loaders `app.include_router(plugin_router)` dynamically.
2. **Database:** Plugins use the shared AsyncSession but must define tables in their own schemas/namespaces, loaded dynamically into SQLAlchemy metadata.
3. **Frontend:** Core templates query the loader for active plugins: `{% for script in plugin_scripts %}<script src="{{script}}"></script>{% endfor %}`.

## 4. AI Gateway (`ai_gateway.py`)

A unified abstraction acting as a reverse-proxy router to Local (Ollama), Open Source (HuggingFace), and Premium (OpenAI/Anthropic) generators.
- Exposes exactly one API: `POST /api/ai/assistant`
- **Routing Logic:** The payload includes `task_type` (e.g., `basic_chat`, `complex_reasoning`, `creative_writing`). The Gateway reads this map and forwards the request transparently to the cheapest/fastest capable provider.

## 5. Review Required

> [!CAUTION]
> The transition to dynamic imports and mounting means standard fast-refresh (Uvicorn `reload`) might not pick up new products instantly without a hard restart unless we write a custom file watcher.

> [!WARNING]
> Security on Plugins: If a plugin contains Python code that is auto-executed by `plugin_loader.py`, it has unrestricted access to the container. We must ensure only verified plugins are placed in the `plugins/` folder.

## Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| **Plugin folder renamed** `cms-core` → `cms_core` | Python can't import hyphenated module names |
| **`JSONB`/`ARRAY` → `JSON`** in ORM models | `JSONB`/`ARRAY` are PostgreSQL-only; `JSON` maps transparently to JSONB on PG and TEXT on SQLite |
| **Plugin loader uses `importlib.import_module`** | Enables relative imports within the plugin package; file-based `spec_from_file_location` breaks package-level imports |
| **`plugin_loader.load_plugins(app)` in conftest** | FastAPI `lifespan` doesn't fire during unit tests with `ASGITransport`; routes must be registered eagerly |
| **`Optional[]` removed from `Mapped[]`** | SQLAlchemy 2.x + Python 3.14 throws `TypeError` with `typing.Optional` in `Mapped[]`; nullability is inferred from `nullable=True` |
| **API prefix `/api/v1/cms/*`** | Versioned endpoints, separate from existing `/api/auth`, `/api/admin`, `/api/ai` |
| **Optimistic locking** via `If-Match` header | Prevents concurrent edits from overwriting — returns `409 Conflict` on stale timestamp |
